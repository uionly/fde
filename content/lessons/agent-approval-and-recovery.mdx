## Approval must change the control path

A confirmation message generated by the model is not human approval. Approval is a durable policy decision tied to a specific action, arguments, actor, and expiry. The execution layer must verify it before performing the action.

<CustomerScenario title="Approval after the fact">
  Northstar's agent issues a $4,800 refund and then asks a supervisor to confirm it in chat. The user interface looks supervised, but the irreversible action already occurred.
</CustomerScenario>

Move the gate immediately before execution. Present the reviewer with the amount, customer, evidence, policy basis, and proposed tool arguments. If any material argument changes, invalidate the approval.

## Design the stopping rules first

Every loop needs explicit limits:

- maximum steps and elapsed time
- per-tool retry budgets with backoff
- cost or token ceilings
- repeated-state detection
- classes of failure that must not be retried
- a safe terminal state and owner for escalation

Without these limits, a temporary 403 can become twenty repeated calls, an incident, and an expensive audit trail. Recovery should preserve the evidence needed for a human or deterministic workflow to continue.

<FDEPrinciple variant="warning">
  High-impact actions require enforceable approval, and every autonomous loop requires a safe way to stop.
</FDEPrinciple>

## Make partial completion explicit

Multi-step actions can fail halfway. Use idempotency keys, compensating actions, and a state machine that distinguishes `proposed`, `approved`, `executing`, `completed`, `failed`, and `needs-review`. Do not let the model infer transaction state from conversational history.

An FDE should rehearse recovery with the customer before launch: tool timeout, revoked permission, stale approval, duplicate event, and unavailable reviewer. The design is production-ready only when these paths are as intentional as the happy path.
