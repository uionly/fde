## Retrieval is an authorization boundary

An answer is not safe merely because the user is authenticated. The retrieval layer must enforce the source permissions that apply to that specific identity.

<CustomerScenario title="A demo that leaks">
  A support specialist asks about refund exceptions. Naive vector search retrieves a manager-only policy because the chunks were indexed without access metadata.
</CustomerScenario>

<FDEPrinciple variant="warning">

## Carry permissions through the lifecycle

Access metadata must be captured during ingestion, updated when source permissions change, and enforced when candidates are generated. Filtering after generation is too late: the model has already received restricted content. Preserve source identifiers and policy versions so an answer can be audited and invalidated when access changes.

Decide how document-level and section-level permissions combine, how groups and regional boundaries are resolved, and what happens when authorization data is unavailable. The safe degraded behavior is usually to return less evidence or route to an approved source—not to search without filters.

## Verify isolation with adversarial cases

Build tests for users with overlapping roles, recently revoked access, cross-tenant vocabulary, manager-only exceptions, and documents whose permissions changed after indexing. Measure both useful retrieval for allowed content and zero exposure for denied content. A high relevance score cannot compensate for one unauthorized candidate.

<Callout title="Architecture review question">
  At each hop, can the team show which identity, resource policy, and tenant boundary produced the authorization decision?
</Callout>

Treat citations as a transparency feature, not a security control. A citation can reveal that leakage occurred; it cannot prevent the restricted chunk from reaching the model. Enforcement belongs in the retrieval and tool control planes.
